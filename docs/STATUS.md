## LLM pipeline (2026-09-29)

- **Model:** `gemma4:26b-a4b-it-mtp-q4_K_M` (official, MoE ~4B active, 18 GB) for chat *and* planning
  (`.env` CHAT_MODEL = LIGHT_MODEL; two models don't fit 24 GB together). Same decode speed as the old
  `huihui_ai/gemma-4-abliterated:e4b` (~110 tok/s, ~200 aggregate with 4 slots) and much better in
  character; stays in character in dark scenes (threats, theft, infidelity), so no abliterated build —
  those glitch (stray foreign tokens, doubled words). Rejected: `qwen3.8:27b` dense (39 tok/s, no
  batching → 6× slower), `qwen3.6:35b-a3b` (23 GB, doesn't fit with KV + embeddings).
- **Ollama 0.35** in `D:\Ollama`, started by `start-game.bat` with `OLLAMA_NUM_PARALLEL=4`,
  `FLASH_ATTENTION=1`, `KV_CACHE_TYPE=q8_0`, `MAX_LOADED_MODELS=2`. Without NUM_PARALLEL Ollama runs one
  request at a time. `LLM_PARALLEL` (.env, default 4) must match it: the chat semaphore holds excess
  requests so priorities apply, with 1 slot held back for each side (dialogue can't starve planning or vice versa).
- Every call pins `num_ctx` 8192 + `keep_alive` 30m (also embeddings); the server warms both models
  at start (`server/ai/warmup.ts`) and names a missing model.
- **Structured output:** plans, replans, decompositions, goal review/pivot/ambition, reflection
  questions/insights, snap and conversation summaries ask for JSON under a schema (`format`):
  enums for locations, goal ids, names, categories; capped lengths. Old line formats still parse.
- **Measured** (same world snapshot, per game day, e4b baseline → current): dialogue LLM turns
  7.8 → 84, turn p50 16.2 s → 1.8 s, plan.daily 27 s → 7 s, truncated replies up to 76% → 0%,
  replans 24 → 8, output tokens 36k → 16k/day, embedding failures 70+ → 0.
- LLM conversations with 4+ lines store each side's first-person takeaway as the memory
  (`conversationSummary.ts`); `LLM_CONVERSATION_SUMMARIES=0` disables.
- **Setting:** the town lives around 1900 (no phones, cars, electricity, internet) — one line,
  `server/ai/setting.ts`, in dialogue, plan and goal prompts. Stops "social media"/"bus" plans.
- **Embeddings:** `qwen3-embedding:0.6b` (beat mxbai 22-15 in a blind retrieval eval,
  `scripts/embed-eval.ts`), queries get Qwen's instruction prefix (`asRetrievalQuery`), every call
  pins `num_ctx` 2048 (at its default 32k it took 4 GB of VRAM and slowed the 26B to ~9 tok/s).
  `app_meta.embedding_model` records which model made the stored vectors; at start and each day
  change `embeddingBackfill.ts` embeds memories without a vector (seeded backstory had none) and
  re-embeds everything after a model change.
- **The Town Crier** (`server/lib/gazette.ts`, `gazette_issues`, router `gazette`, UI
  `src/components/ui/Gazette.tsx`): at each day change the model writes a period newspaper from the
  day's important feed lines (rumor retellings collapsed) and chronicle arcs — headline, 2-4
  articles led by the human story, gossip column. "📰 Paper" in the TopBar, archive, "Print
  today's edition". `LLM_GAZETTE=0` disables.
- MTP vs plain Gemma 4 26B measured on replayed game traffic: MTP 29% faster (126 s vs 163 s).
  `gemma4:26b-a4b-it-q4_K_M` (17 GB) is installed but unused. With OLLAMA_MAX_LOADED_MODELS=2 a
  third model (e.g. a second embedder in scripts) waits forever for the busy chat model to be
  evicted — `ollama stop` it first.

## Tooling

- **Aseprite pipeline** (`D:\SteamLibrary\steamapps\common\Aseprite\Aseprite.exe`, 1.3.18): every
  sprite set is a batch Lua script that writes `.aseprite` sources + the PNG the client loads.
  Re-run after editing: `Aseprite.exe -b --script-param dir=<out> --script scripts/aseprite/<x>.lua`.
  `agent-sheets.lua` (derives 11-frame sheets from `public/sprites/agents/<name>.png`),
  `roof-tiles.lua`, `nature-props.lua`, `furniture.lua`, `emotes.lua`, `beat-fx.lua`,
  `held-items.lua`, `event-decor.lua`, `critters.lua`, `portrait-moods.lua`. Every script's frame
  order is mirrored in a `*Frames.ts` table next to its consumer — keep them in sync.
- **Canvas systems** (`src/components/canvas/systems/`): pluggable per-feature renderers, one line
  each in `systems/index.ts` (contract in `systems/types.ts`). `?nosystems` in the URL disables them
  all for A/B frame-time checks; `node docs/scratch/probe-living-canvas.mjs` (verify server running)
  triggers an event + an intervention, samples fps and lists atlas loads and console errors.

- `npm run check` — gate (tsc + vitest).
- **LLM tooling:** `LLM_TRACE=data/trace/x.jsonl` on the server appends every LLM request/reply;
  `npx tsx scripts/llm-bench.ts --trace x.jsonl --models a,b [--offline]` replays it against models
  at a concurrency and scores replies with the game's own parsers; `npx tsx scripts/llm-smoke.ts
  --model m` sends one of each structured prompt. Per-purpose latency is in the 🧠 tooltip
  (`world.getLLMMetrics`). Capture recipe: snapshot the live DB with `better-sqlite3` `.backup()`
  into the worktree's `data/verify.db`, run `SERVER_PORT=3011 DATABASE_PATH=./data/verify.db
  LLM_TRACE=… npx tsx server/index.ts`, watch it with launch config `little-life-client-3011`.
- `npm run deadcode` — orphan files / unused exports.
- `npm run soak -- --days 5 [--tick-speed 4] [--db data/verify.db]` — headless multi-day run with
  the LLM disabled (template tier), on a temp DB copy; prints a daily economy table and flags
  anomalies. Refuses `data/little-life.db`. ~2 min per game day at speed 1.
- Playtest recipe (real LLM): copy `data/little-life.db*` → `data/verify.db*`, run the server with
  `DATABASE_PATH=./data/verify.db`, sample the DB read-only. See CLAUDE.md "Live verification".

## DB migration note

`server/db/clockMigration.ts` rebases old tick stamps to game minutes once per DB file
(`PRAGMA user_version` 0 → 2) the first time any process opens it through `server/db`. Verified on a
copy of the live world (tick 15 → stamps 1981/1980, second run no-op). Backup taken before the
change: `data/backup-2026-09-29-pre-gameclock/`. Running **old** code against a migrated DB would
write tick stamps into minute columns — don't switch back to pre-2026-09-29 branches on the same DB.
